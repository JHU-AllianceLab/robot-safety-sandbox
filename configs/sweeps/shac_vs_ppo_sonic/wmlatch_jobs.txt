# Is the world-model filter too LATE, or does it hand back too SOON? Same 512 kicked
# held-out episodes per seed as wmmin_jobs.txt (--seed 0 lists, kick at the start, sensor
# noise OFF), the same tube tables (wmmin_calib/<tag>/min_tube.json):
#   <cond>+latch: from the filter's first hand-over on, SHAC keeps the episode. If the
#     latched filter survives about as often as SHAC alone (~94 %), its first trigger was in
#     time and the failures come from handing control back to SONIC; if not, it fired late.
#   next to the unlatched wmmin:0.4:0.95 / wmrollout:1 and the exact CPU filter rollout:1,
#   with the new per-episode hand-over count (tel_switches, switches_per_episode_post).
# shac_s0 also renders 9 episodes (filter_video.py): 5 where the WM tube filter falls
# while SHAC alone survives (2 3 5 13 44), 2 it saves (384 125), 1 it breaks (379), 1 where
# all survive (9); panels SONIC alone | WM tube filter | latched | exact-sim filter | SHAC.
# Run through wmlatch.sh (a smoke test first). ~15 min per seed on one GPU + 30 CPUs.
python examples/eval_sonic_qcbf.py --policy runs/shac_vs_ppo_sonic/shac_s0/g1_recover_safetyshac1p/final_model.zip --tag shac_s0 --sonic-dir $HOME/gear_sonic_hf --hip mjlab --suites push --episodes 512 --num-envs 256 --onset-s 0.02 0.02 --no-obs-noise --rollout-workers 30 --conditions sonic fallback wmmin:0.4:0.95 wmrollout:1 rollout:1 wmmin:0.1:0.95+latch wmmin:0.4:0.9+latch wmmin:0.4:0.95+latch wmmin:1:0.95+latch wmmin:3:0.95+latch wmrollout:0.4+latch wmrollout:1+latch wmrollout:3+latch --tube-calib runs/shac_vs_ppo_sonic/wmmin_calib/shac_s0/min_tube.json --video-episodes 2 3 5 13 44 384 125 379 9 --video-conditions sonic wmmin:0.4:0.95 wmmin:0.4:0.95+latch rollout:1 fallback --out runs/shac_vs_ppo_sonic/wmlatch_eval/shac_s0  # creates: runs/shac_vs_ppo_sonic/wmlatch_eval/shac_s0/push.json
